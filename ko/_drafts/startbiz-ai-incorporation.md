## 시작

평화로운 월요일 아침...

> \>내 상황을 상상해보자.  
> \>StartBiz로 내 스타트업 법인 설립하려고 함.  
> \>전용 클라이언트로 법인인감을 제출하라고 함.  
> \>스캐너를 요구함. 근데 요즘 누가 스캐너를 갖고 있음?  
> \>"이제 공식 스마트폰 앱으로도 인감을 제출할 수 있습니다!"  
> \>앱스토어에서 찾아봄 -> 없음.  
> \>구글 스토어에서 찾아봄 -> 내 지역에서는 이용 불가.  
> \>괜찮음. 인쇄소에 가면 됨.  
> \>"죄송하지만 네트워크에 연결된 스캐너는 지원하지 않습니다. TWAIN 호환 USB 드라이브에 연결된 스캐너만 지원합니다."
{: .greentext}

집에 돌아왔을 때는 완전히 박살 나고 패배한 기분이었다. 아무것도 이해되지 않았다. 보안에 대한 잘못된 확신에 사로잡힌 누군가가 스캔한 자료를 단일 인터페이스로만 받도록 요구한 게 분명했다. 사용자에게 공감하는 누군가가 사용자 친화적인 대안을 내놓았다. **그런데 그게 작동을 안 한다고!**

남은 선택지는 다음과 같았다:

1. 동네의 모든 인쇄소에 전화해서 스캐너가 TWAIN 호환 USB 드라이브에 유선으로 연결되어 있는지 묻는다.
2. 스캐너를 산다.
3. 클라이언트를 디스어셈블해서 뭘 하는지 알아본다.

나는 1번이나 2번을 할 정도로 미치지는 않았다. 세 번째 선택지의 유일한 문제는 소프트웨어를 리버스 엔지니어링해 본 지 꽤 오래됐다는 거였다. 예전에 컴퓨터 네트워킹을 배우거나 비디오게임 콘솔의 하드웨어 개조를 하며 놀 때 몇 번 해 본 적은 있었다.

## 해결

오래된 문제. 현대적인 해결책. OpenCode 세션을 하나 열고 Astra에게 `ImageDocScan.exe`를 디스어셈블해서 살펴봐 달라고 했다. StartBiz가 내 시스템에 설치한 이 프로그램은 TWAIN/ActiveX 컴포넌트를 사용하는 32비트 .NET Windows Forms 애플리케이션이었다. Astra는 .NET의 리플렉션 API를 사용해 어셈블리의 클래스/필드와 컴파일된 중간 언어를 살펴봤다.

미친 건 이거다. 이 클라이언트는 **JPEG, PNG, BMP, 그리고 TIFF를 지원하고 있었다.** 스캐너 입력과 똑같은 인감 추출 루틴을 쓰는 `loadImageButton_Click`이 멀쩡히 있었는데, 버튼의 표시 여부를 정하는 플래그만 `false`로 설정되어 있었다.

결국 할 일은 브라우저의 스캔 세션 파라미터와 애플리케이션의 작업 경로를 가로채고, 아래 코드를 실행하는 것뿐이었다:

```powershell
$field = $formType.GetField("loadImageButton", $flags)
$button = $field.GetValue($form)
$button.Visible = $true
```

이렇게 하니 숨겨진 버튼이 나타났다. 그래서 법인인감 사진을 찍어 해킹한 클라이언트에 jpg 파일을 넣었고... 잘 됐다.

## 결론

서류에 전부 서명하고 법인 설립 신청서를 제출했다. 그리고 다음 날 승인됐다.

모든 게 그냥 미친 것 같았다. 간단한 비디오게임이나 인스턴트 메시징 서비스를 리버스 엔지니어링하던 시절이 기억난다. 제출 폼을 살펴보며 어떤 API 호출이 일어나는지 알아보는 것. 어떤 에셋이 있는지. 헤더를 스니핑하면서 페이로드의 구조를 파악하는 것. 요청이 어디로 보내지는지 등등. 이런 것들은 나한테 주말 하나를 통째로 잡아먹는 일이었다. 그리고 지금은 감이 무뎌져서 아마 못 할 거다. 그런데 이제는 AI 모델에 최소한의 가이드만 줘도 일을 끝낼 수 있다. 솔직히 좀 재미있기도 했다. 내 지식으로 가설을 빠르게 시험해 보고, 단순하고 기계적인 작업은 AI 모델로 쭉 처리하면서 과정을 더 잘 이해해 가는 게 재미있었다.

그러니 AI를 갖고 놀 새로운 방법을 찾고 있다면, 관심 있는 시스템이나 문제를 리버스 엔지니어링하는 데 한번 써 보길 권한다. 수학적 반례를 찾는 데 효과적인 것과 비슷한 느낌이다. AI 에이전트가 실제로 시스템을 만드는 것보다 취약점을 찾고 시스템의 허점을 이용하는 데 더 잘 맞는다고 해도, 나는 놀라지 않을 것 같다.
